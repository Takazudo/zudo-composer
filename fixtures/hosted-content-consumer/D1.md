# Local Worker/D1 adapter and Article host

Host-owned reference code in this independently installed fixture. It uses only
the public `zudo-composer/hosted-content` and `zudo-composer/hosted-content/testing`
entries. Nothing here enters a Composer runtime graph or the shipped package,
and nothing adds D1, Wrangler or Cloudflare dependencies to Composer itself.

This is **local evidence only**: the pinned local workerd (through Miniflare,
already a consumer dev dependency) and its D1 implementation. No Cloudflare
account, remote binding, production D1, deployment or synchronization is used.

| File | Runs in | Role |
| --- | --- | --- |
| `d1-storage.mjs` | workerd and Node (binding proxy) | `HostedStorage` and the Content-AI proposal store over one D1 binding |
| `d1-runtime.mjs` | Node launcher only | Starts workerd with one local D1 binding in a host-owned directory; refuses remote |
| `d1-proof.mjs` | Node + workerd | Local Worker/D1 binding proof and report |
| `article-cms/article-core.mjs`, `api.mjs`, `d1-article.mjs`, `render.mjs` | Both hosts | Runtime-neutral Article definition, Content-AI wiring, HTTP contract, D1 publication |
| `article-cms/worker.mjs` | workerd | Worker composition root |
| `article-cms/worker-host.mjs` | Node launcher only | Bundles once, initializes, serves on loopback |
| `article-cms/worker-host-proof.mjs`, `journey-proof.mjs` | Node + workerd + Chromium | Worker host boundaries; the shared Node/SQLite vs Worker/D1 journey |

## Storage contract on D1

- **One batch per accepted command.** `commit` sends, as one `batch()`:
  1. a precondition guard: `INSERT INTO hosted_commit_guard (ok) SELECT NULL
     WHERE ?proposed IS ?expected OR NOT EXISTS (SELECT 1 FROM hosted_head WHERE
     id = 1 AND version = ?expected)`. `hosted_commit_guard.ok` is `NOT NULL`, so
     the insert fails, and the whole batch rolls back, unless the head exists at
     the expected version and the proposed version is different;
  2. the head `UPDATE … WHERE id = 1 AND version = ?expected`;
  3. a postcondition guard, `INSERT … SELECT NULL WHERE changes() <> 1`, which
     aborts the batch unless that `UPDATE` itself changed exactly one row;
  4. the insert-only receipt, snapshot and revision rows and the publication
     upsert.

  D1 runs a batch as one SQL transaction and rolls it back when any statement
  fails, so the decision is made inside the database before anything else is
  written. The previous guard only checked, after the `UPDATE`, that the
  stored version equalled the proposed one. When the proposed version was
  already the stored version (a reused version), that check passed although
  the `UPDATE` matched no row, and the receipt and other rows committed. The
  adapter's later check of `meta.changes` could not undo a completed batch. It
  was a shared adapter defect, inherited by the SQLite fixture, not something
  the Article UI introduced. The `meta.changes` check remains as a defensive
  second line only. There is no JavaScript lock and no transaction across an
  await, and one command is never split into several batches.
- **Reused versions.** A commit whose proposed version equals `expectedVersion`
  is refused with nothing written, as in the memory reference. A commit whose
  proposed version equals the currently stored version but whose
  `expectedVersion` is stale is refused the same way. The service issues a fresh
  version id for every change, so this only happens with a stale or replayed
  change, never with a legitimate one.
- **Outcome classes.** Only these definite constraint refusals resolve `false`
  (a definite refusal: nothing was written; the service re-reads and retries):
  either guard, a duplicate receipt `(actor_id, operation_key)`, snapshot id,
  revision id or revision `(entry, sequence)`. Every other D1 statement error is
  `HostedD1Error` with `outcome: "failed"` (`storage-failed`): the batch rolled
  back. A timeout, lost response or transport error is `outcome: "unknown"`
  (`storage-outcome-unknown`): the write may still commit, so the caller keeps
  the same operation key and recovers through the receipt. A timeout is never
  treated as proof that nothing was written. None of these is reported as a
  revision conflict.
- **Limits** (documented D1 limits, checked 2026-11-01): 2,000,000 bytes per
  row/string, 100 bound parameters, 100,000-byte SQL, 30 s per batch. Each
  statement is checked before submission and an oversized commit is refused
  with `outcome: "limit"` (`storage-limit`) and nothing written. The adapter's
  own wait is 35 s by default.
- **Reads.** Keyed or keyed-paginated (`listRevisions` uses `sequence < ? ORDER
  BY sequence DESC LIMIT ?`); every value is parsed per call, so it is
  detached. Ordinary reads never load history or receipts.
- **Consistency.** No Sessions API and no read replicas: every query goes to
  the primary, so a read after a committed batch observes it. Read-replica
  optimization is out of scope for this slice.
- **Dump.** `dumpD1Database` reads every table in one batch, which D1 runs as
  one transaction, so the capture is coherent while other writers continue.
- **Proposals.** `createD1ProposalStore(db, { owner })` is create-only
  (`operation-key-reuse` on a duplicate id), bound to one trusted owner (another
  owner is refused on create and not found on read) and lives beside, never
  inside, the Content tables. Preparing a proposal writes only this row.
- **Initialization.** `initializeD1Database(db, seed, { hostTables })` first
  classifies the database without writing anything (`classifyD1Database`):
  - **empty** (no schema object except local D1's own `_cf_METADATA` table,
    which is ignored by that exact name only): it is created. The tables, any
    host-declared tables (the Article host declares `article_artifact`), the
    `hosted-d1-v1` marker and the complete seed go in one batch, so the store is
    either complete or absent. That batch starts with a guard that aborts it if
    any other object appeared after the classification, and uses plain
    `CREATE TABLE`, so a racing initializer's batch fails whole. The loser
    reclassifies and reopens the winner's store; two seeds never mix.
  - **current** (exactly the store's tables and host tables with identical
    definitions as stored in `sqlite_schema`, their implicit unique indexes and
    nothing else, one marker row naming `hosted-d1-v1`, one head row): it is
    reopened with no write at all, so existing data, proposals and Article
    artifacts are untouched.
  - **foreign** (unknown tables, indexes, views or triggers; a missing or altered
    table or constraint; an older or malformed marker; a missing head): refused
    with `HostedD1Error` `outcome: "incompatible"` (`storage-incompatible`)
    and left unchanged. Nothing is created, stamped, repaired, migrated or reset.
    The Worker launcher refuses to start on such a directory.

  The seed's shape and D1 limits are checked before the classification, so an
  invalid seed writes nothing. There is no migration framework and no pruning or
  recycling of operation identities.
## Proofs

```sh
node d1-proof.mjs <work dir>                         # writes <work dir>/d1-proof-report.json
node article-cms/worker-host-proof.mjs <work dir>
node article-cms/journey-proof.mjs <work dir> <failure artifacts dir>   # Chromium
```

`d1-proof.mjs` runs:

1. The shipped `runHostedContentConformance` (16 scenarios) from Node, every
   storage call through Miniflare's binding proxy into workerd's local D1.
   `restart()` disposes the workerd process and starts a new one on the same
   directory without seeding. The `conditional-commit-version-guard` scenario
   refuses stale, reused and unchanged versions combined with head-only,
   receipt and revision, snapshot and publication upsert, publication-only
   (receipt-free) and all-record changes, and a delayed original that carries
   the version a competing handle stored first. Each refusal compares the head
   (including its version), the complete logical dump and the existing
   publication row before and after.
2. The same runner bundled with the adapter into one Worker, executing inside
   workerd against `env.DB` (no process restart in this lane).
3. D1-specific cases: zero-row head update, duplicate revision id and
   duplicate `(entry, sequence)` rolling back head and receipt; a missing head
   refusing every commit with no orphaned row, and the `changes()` guard
   aborting a batch after a zero-row `UPDATE`; a real `CHECK` failure right
   after the head `UPDATE`; a response lost after the durable batch, recovered
   once, and a reused key with another request refused; a wait that times out
   while the batch is held in flight, which then commits and is recovered under
   the same key, and a retry that wins first making the late original refuse;
   a local limit refusal; stopping workerd with a batch in flight (all or
   nothing after reopen); restart without seed and a no-op re-initialization;
   proposals surviving restart.
4. Initialization, one real local D1 database per case: an empty database; a
   populated store reopened and restarted without any write; an older marker
   alone; an older marker with its own tables and rows; unrelated tables and
   rows without a marker; a malformed marker; the current marker with a missing
   constraint; a complete structure without a head; a core store opened by a
   host that declares its own table; an Article store whose artifact row
   survives reopening; and concurrent first starts (five free races, one held
   interleaving where the late initializer reopens the early one's store, and
   an object appearing after classification aborting creation). "Unchanged"
   means `snapshotD1Database` is identical before and after: every
   `sqlite_schema` object with its definition (including `_cf_METADATA`) and
   every row of every other table.

Injected faults are proof hooks passed only by these proofs (`proof` option),
never by a host: a failing statement inside the real batch, a held submission,
or a discarded response after completion. They never forge a receipt or change
a service response. Production network partitions, primary failover, replica
lag and Cloudflare-side resets are not reproducible locally.

`journey-proof.mjs` runs the same Article scenario against `server.mjs`
(Node/SQLite) and `worker-host.mjs` (Worker/local D1), each in its own
directory, and compares values, provenance and operation shapes (not ids,
timestamps or versions). The fake provider is deterministic and is not
real-model evidence; real-model and physical-device acceptance remain separate.
