# Local Worker/D1 adapter and Article host

Host-owned reference code in this independently installed fixture. It uses only
the public `zudo-composer/hosted-content` and `zudo-composer/hosted-content/testing`
entries. Nothing here enters a Composer runtime graph or the shipped package,
and nothing adds D1, Wrangler or Cloudflare dependencies to Composer itself.

This is **local evidence only**: the pinned local workerd (through Miniflare,
already a consumer dev dependency) and its D1 implementation. No Cloudflare
account, remote binding, production D1, deployment or synchronization is used.

| File | Runs in | Role |
| --- | --- | --- |
| `d1-storage.mjs` | workerd and Node (binding proxy) | `HostedStorage` and the Content-AI proposal store over one D1 binding |
| `d1-runtime.mjs` | Node launcher only | Starts workerd with one local D1 binding in a host-owned directory; refuses remote |
| `d1-proof.mjs` | Node + workerd | Local Worker/D1 binding proof and report |
| `article-cms/article-core.mjs`, `api.mjs`, `d1-article.mjs`, `render.mjs` | Both hosts | Runtime-neutral Article definition, Content-AI wiring, HTTP contract, D1 publication |
| `article-cms/worker.mjs` | workerd | Worker composition root |
| `article-cms/worker-host.mjs` | Node launcher only | Bundles once, initializes, serves on loopback |
| `article-cms/worker-host-proof.mjs`, `journey-proof.mjs` | Node + workerd + Chromium | Worker host boundaries; the shared Node/SQLite vs Worker/D1 journey |

## Storage contract on D1

- **One batch per accepted command.** `commit` sends the head
  `UPDATE … WHERE version = ?`, a guard `INSERT` into the always-empty
  `hosted_commit_guard` (it fails `NOT NULL` when the head update matched zero
  rows), the insert-only receipt, snapshot and revision rows and the
  publication upsert as one `batch()`. D1 runs a batch as one SQL transaction
  and rolls it back when any statement fails, so preconditions are enforced
  inside the database. There is no JavaScript lock and no transaction across an
  await, and one command is never split into several batches.
- **Outcome classes.** Only these definite constraint refusals resolve `false`
  (nothing written; the service re-reads and retries): the guard, a duplicate
  receipt `(actor_id, operation_key)`, snapshot id, revision id or revision
  `(entry, sequence)`. Every other D1 statement error is
  `HostedD1Error` with `outcome: "failed"` (`storage-failed`): the batch rolled
  back. A timeout, lost response or transport error is `outcome: "unknown"`
  (`storage-outcome-unknown`): the write may still commit, so the caller keeps
  the same operation key and recovers through the receipt. None of these is
  reported as a revision conflict.
- **Limits** (documented D1 limits, checked 2026-11-01): 2,000,000 bytes per
  row/string, 100 bound parameters, 100,000-byte SQL, 30 s per batch. Each
  statement is checked before submission and an oversized commit is refused
  with `outcome: "limit"` (`storage-limit`) and nothing written. The adapter's
  own wait is 35 s by default.
- **Reads.** Keyed or keyed-paginated (`listRevisions` uses `sequence < ? ORDER
  BY sequence DESC LIMIT ?`); every value is parsed per call, so it is
  detached. Ordinary reads never load history or receipts.
- **Consistency.** No Sessions API and no read replicas: every query goes to
  the primary, so a read after a committed batch observes it. Read-replica
  optimization is out of scope for this slice.
- **Dump.** `dumpD1Database` reads every table in one batch, which D1 runs as
  one transaction, so the capture is coherent while other writers continue.
- **Proposals.** `createD1ProposalStore(db, { owner })` is create-only
  (`operation-key-reuse` on a duplicate id), bound to one trusted owner (another
  owner is refused on create and not found on read) and lives beside, never
  inside, the Content tables. Preparing a proposal writes only this row.
- **Initialization.** `initializeD1Database(db, seed)` is explicit: it creates
  the current schema (`hosted-d1-v1`) and seeds in one batch whose every seed
  row is conditional on an absent head, so a repeated or racing start never
  resets or reseeds. A database recorded under another schema version is
  refused unchanged; there is no migration framework. No pruning or recycling
  of operation identities.

## Proofs

```sh
node d1-proof.mjs <work dir>                         # writes <work dir>/d1-proof-report.json
node article-cms/worker-host-proof.mjs <work dir>
node article-cms/journey-proof.mjs <work dir> <failure artifacts dir>   # Chromium
```

`d1-proof.mjs` runs:

1. The shipped `runHostedContentConformance` (15 scenarios) from Node, every
   storage call through Miniflare's binding proxy into workerd's local D1.
   `restart()` disposes the workerd process and starts a new one on the same
   directory without seeding.
2. The same runner bundled with the adapter into one Worker, executing inside
   workerd against `env.DB` (no process restart in this lane).
3. D1-specific cases: zero-row head update, duplicate revision id and
   duplicate `(entry, sequence)` rolling back head and receipt; a real `CHECK`
   failure right after the head `UPDATE`; a response lost after the durable
   batch, recovered once, and a reused key with another request refused; a
   wait that times out while the batch is held in flight, which then commits
   and is recovered under the same key, and a retry that wins first making the
   late original refuse; a local limit refusal; stopping workerd with a batch in
   flight (all or nothing after reopen); restart without seed and a no-op
   re-initialization; proposals surviving restart; a foreign schema refused.

Injected faults are proof hooks passed only by these proofs (`proof` option),
never by a host: a failing statement inside the real batch, a held submission,
or a discarded response after completion. They never forge a receipt or change
a service response. Production network partitions, primary failover, replica
lag and Cloudflare-side resets are not reproducible locally.

`journey-proof.mjs` runs the same Article scenario against `server.mjs`
(Node/SQLite) and `worker-host.mjs` (Worker/local D1), each in its own
directory, and compares values, provenance and operation shapes (not ids,
timestamps or versions). The fake provider is deterministic and is not
real-model evidence; real-model and physical-device acceptance remain separate.
